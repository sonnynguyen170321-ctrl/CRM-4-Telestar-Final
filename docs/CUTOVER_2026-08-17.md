## What changed in this release

Three commits on top of `1bb0336`:

| SHA | Change |
| --- | --- |
| `fb6f40a` | sidebar no longer claims a role before the session answers; dead Google Font origins dropped from CSP (cherry-picked from `all-green/wave-3-feature-security`) |
| `15d0885` | `POST /api/client-reports/preview` validates its references before metrics are built |
| `ff09dce` | `POST /api/leads/import` validates `campaignId` before the batch exists |

Both security commits close request-reference gaps that were live on `main`. Measured against
pre-fix code, as an ordinary SDR in tenant A:

- **preview** returned `200` carrying another tenant's client name and metrics; an in-tenant
  client the caller could not see returned its numbers too; a nonexistent client returned `500`.
  `leadgen` — a role refused outright by the create route — was served in full.
- **import** returned `202` and created an `ImportBatch` pointing at another tenant's campaign.
  `Campaign` ids are unique globally, so the foreign key was satisfied and nothing complained.

Both now use the same helpers as the four surfaces that already had them
(`canReferenceClient` / `canReferenceCampaign`, `404` for foreign-or-missing so existence is
never confirmable, `403` for a real in-tenant record the caller may not use, `422` for a
client/campaign mismatch). No new policy was written.

### One behaviour change worth announcing

`POST /api/leads/import` now refuses a campaign the caller cannot reference. For every role
except **director** and **leadgen manager**, "can reference" resolves to the campaigns the
caller's visible users are assigned to via `CampaignSdr` — so **an import into a campaign with
no members is refused with 403**, including for a floor manager.

This is not new policy; it is `POST /api/leads` behaviour, which import did not share. The
practical consequence is an ordering requirement:

> **Create the campaign → assign at least one member → then import.**

`tests/admin.test.ts` had a fixture asserting the opposite. It was corrected, not the check.

## The preflight — run this first, and again before the final GO

```bash
CUTOVER_BASE_URL=https://<host> \
CUTOVER_BACKUP_ID=<snapshot-id> CUTOVER_BACKUP_AT=<iso-8601-utc> \
CUTOVER_TENANT_ID=<tenant> \
  npm run cutover:preflight
```

Mechanically decides the conditions the release policy calls mandatory: HTTPS, TLS expiry, HSTS,
Secure cookie, whether the published demo password still opens an account, a recorded pre-cutover
backup, migration currency, both email safety flags, and a real enqueue-to-completed round trip.
Exits non-zero on any blocking failure.

It does **not** replace `npm run prod:audit`, `./scripts/post-deploy-smoke.sh` or
`npm run check:relational-integrity` — it prints those as follow-ups. Run all four.

Two things it will not do: treat an unreachable host as a pass (every undetermined fact is a
failure), or report a clean `GO` while any declared exception is open.

> **`npm run worker:healthcheck` was repaired in this release.** The previous inline form died at
> `MODULE_NOT_FOUND` and, had it loaded, would have thrown `requires a tenantId`. If you have run
> it before and taken a silent failure for success, the queue has never actually been proven.

### The deployment-method decision

There must be exactly one deploy command and one rollback command when this phase ends. Two
routes:

- **Update the box's checkout** to the release SHA so `deploy.sh` / `rollback.sh` and
  `deployments.ndjson` work. `IMAGE_TAG` must be replaced by a `CRM_IMAGE` digest **in the same
  change** — the repo's compose refuses to start without it. Do this deliberately, never
  mid-incident.
- **Or keep the stale checkout** for this cutover and use the box's documented invocation,
  recording the deploy manually. Then carry "deploy tooling not in use on the box" as declared
  debt rather than pretending it is closed.

The box's working invocation, if the checkout stays stale:

```bash
cd /opt/crm-4-u
# dry run first — changes nothing, prints what compose actually resolved
sudo APP_ENV_FILE=.env.production docker compose \
  -f docker-compose.yml -f docker-compose.aws.yml \
  --env-file .env.production config --images

sudo APP_ENV_FILE=.env.production docker compose \
  -f docker-compose.yml -f docker-compose.aws.yml \
  --env-file .env.production up -d --no-deps web worker
```

`--no-deps` matters: the base compose defines a local `postgres` this box does not use.

> **The failure mode:** if the image variable is edited and the compose command *then* fails,
> the env file names the new image while old containers keep running. The site looks fine and
> the next compose run — or a reboot — silently applies an unverified deploy. Finish or revert;
> never stop in between.

## Phase 5 — Security and environment gates

### HTTPS — blocking

Internal credentials must not cross a network in clear text. Verify `CRM_DOMAIN`,
`CADDY_SITE_ADDRESS` and `NEXTAUTH_URL` agree, then prove it from a real client:

```bash
curl -sSI http://<host>/            # expect 301/308 to https
curl -sSI https://<host>/login      # expect 200 + Strict-Transport-Security
curl -sS  https://<host>/api/health
openssl s_client -connect <host>:443 -servername <host> </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates -issuer
```

Then in a browser: log in, confirm the session cookie is `Secure` + `HttpOnly`, confirm no
mixed-content warnings in the console. Configuration text alone is not sign-off.

### Credentials

```bash
node --env-file=.env.production node_modules/tsx/dist/cli.mjs scripts/list-users.ts
```

For every demo/test account: rotate to a unique credential if the persona is needed, deactivate
it if not. The previously published shared demo password must not remain usable on **any**
account. Confirm the role did not change, and that `authVersion` incremented so prior sessions
are revoked.

`scripts/create-user.ts` has `--deactivate` and revokes sessions (PR #44 — see Phase 16).
**Never use `create-admin` to rotate a non-Director persona**; it grants director.

### Secrets

Confirm production carries fresh values for `AUTH_SECRET`, `ENCRYPTION_KEY`, `CRON_SECRET`,
database and Redis credentials, mailbox/OAuth credentials, and any AI/research provider keys in
use. `npm run prod:check-env` validates presence against `lib/env-contract.ts`. Record
**presence and rotation date only**.

### CSP

**CSP is report-only today. It is not enforcing.** Do not record otherwise.

Enforcement may ship as an isolated, browser-tested PR if it does not destabilise the release;
otherwise carry it as post-cutover security debt. It is not a reason to delay HTTPS.

## Phase 6 — Backup and recovery gate

Before any real data is imported:

1. Enable automated Cloud SQL backups and set retention.
2. Take an immediate pre-cutover snapshot; record its identifier and UTC timestamp.
3. **Prove the restore.** Restore the snapshot into a scratch instance and run a row count
   against it. An untested backup is not a rollback path.

```bash
gcloud sql backups create --instance=<instance>
gcloud sql backups list --instance=<instance> --limit=5
gcloud sql instances clone <instance> <scratch-instance> --point-in-time=<ts>
```

Then, and only then:

```bash
node node_modules/prisma/build/index.js migrate status
node node_modules/prisma/build/index.js migrate deploy
node node_modules/prisma/build/index.js migrate status   # must report current
```

**Never** `prisma migrate reset`, **never** `prisma db push` as a production substitute, and
**never** a destructive seed — `prisma/seed.ts` still carries 17 unguarded `deleteMany()` calls
including `tenant` and `user`, and `package.json` wires it to `prisma.seed`.

RLS: prove on staging or a clone with `npm run verify:rls` **before** enabling in production, and
reapply `supabase/rls.sql` after any migration that adds a tenant-owned table — Prisma migrations
deliberately contain no `ENABLE`/`FORCE`/`CREATE POLICY`.

## Phase 7 — Redis and worker proof

CI Redis is not production Redis. Prefer a managed instance over a container whose data dies with
the VM.

Verify: TLS/auth, worker connects, queues connect, enqueue → active → completed, delayed jobs,
reconnect after interruption, worker recovery, failed-job visibility, queue depth, `JobRun`
reconciliation, behaviour after a Redis restart, persistence configuration, and an eviction policy
appropriate for BullMQ (**`noeviction`** — BullMQ data is not a cache and must not be evicted).

```bash
npm run worker:healthcheck     # then confirm the JobRun reaches completed
redis-cli -u "$REDIS_URL" CONFIG GET maxmemory-policy
redis-cli -u "$REDIS_URL" CONFIG GET appendonly
```

If managed Redis cannot be introduced first, do **not** record the risk as closed. Record local
Redis as a temporary internal-use exception with: autosend disabled, database treated as source of
truth, reconciliation proven, recovery documented.

`docs/MIGRATION_RUNBOOK.md` is stale — do not follow it mechanically.

```env

```

Rehearsal is green only when the data **reconciles** — not when the importer exits zero. If a
repair is needed, fix the script or the deterministic transform and rerun from a fresh database.
Never hand-massage rows you cannot reproduce in production.

Production cutover order (each step gated on the previous):

freeze source writes / record the delta cutoff → record UTC **and** Asia/Ho_Chi_Minh timestamps →
confirm backup → confirm rollback command → pause workers that could mutate imported records →
autosend off, dry-run on → export final source snapshot → hash and archive the inputs →
`migrate deploy` → data migration → reconciliation → `npm run check:relational-integrity` →
**only then** restart workers and scheduler.

If reconciliation fails: repair or roll back. Do not continue into acceptance.

## Phases 11–14 — Acceptance on the deployed release

Test the deployment, not localhost. Both directions for every role — the user can do their own
job, and cannot do someone else's.

| Role | Positive | Negative |
| --- | --- | --- |
| Director | dashboards, users, clients, campaigns, reporting, admin, workers | — |
| Floor Manager | campaign/team management, reporting, meeting oversight, queue surfaces | admin actions above their level |
| Team Lead | pod SDRs, assigned campaigns, leads, coaching, meetings, opportunities | another team's objects denied |
| SDR | lead → activity → task → sequence → inbox → reply → meeting → opportunity | peer/private objects outside scope |
| Leadgen Manager | CSV import → pool → dedupe → qualification → requirement → distribution → conversion → metrics | — |
| Leadgen | scoped research/qualification | cannot exceed assigned campaign/team scope |

**Phase 12 golden journey** — one controlled record through the whole chain, capturing the record
id at each hop: intake → pool → qualification → campaign assignment → SDR assignment → working
lead → sequence enrollment → activities/tasks → reply handling → meeting booked → outcome →
opportunity → pipeline stage → client report. Every transition must leave the correct durable
record and audit trail. `tests/golden-journey.test.ts` asserts this chain in CI; this phase proves
it on the deployed release.

**Phase 13 email** — sequence creation, multiple scheduled steps, day/time windows, business-day
handling, enrollment, scheduling, pause/resume, manual ownership, suppression, daily quota,
dry-run worker, `OutboundMessage` ledger, idempotency, reply detection, bounce detection,
stop/unsubscribe. **No real client receives a test email.** If a live-provider smoke is required,
use a Telestar-owned sender *and* a Telestar-owned recipient.

> Do **not** set `SEQUENCE_AUTOSEND_ENABLED=true` or `EMAIL_SEND_DRY_RUN=false` as part of this
> cutover. Live autosend is a separate go-live decision after internal validation.

**Phase 14 scheduler/ops** — confirm the sequence engine, inbox sync, email health and maintenance
jobs are installed and firing; `CRON_SECRET` authenticates; recent successful executions appear in
logs; failures surface rather than vanish. Check `/api/health`, the worker-health surface, DB and
Redis connectivity, queue health, failed and stale jobs, reconciliation, log access, audit
retention.

## Rollback

| Situation | Action |
| --- | --- |
| Bad image, no migration ran | redeploy the previous digest (`PREVIOUS_CRM_IMAGE`, or the previous `IMAGE_TAG` on the stale checkout) |
| Bad image, additive migration ran | redeploy previous digest; additive migrations are forward-compatible |
| Bad image, destructive migration ran | restore the Cloud SQL snapshot from Phase 6 — the only path |
| Migrated data wrong | restore the snapshot; do not repair in place |

Consult `deployments.ndjson` (or the manual record) before rolling back across a schema change.

## Release policy

**NO-GO** — unreconciled migrated data · missing pre-cutover backup · untested rollback · broken
authentication · cross-tenant disclosure or write · role escalation · failed migration · failing
required CI · broken worker/import path · production running a SHA other than the certified one ·
exposed shared credentials · plain HTTP for normal users over an untrusted network.

**GO FOR INTERNAL USE WITH DECLARED EXCEPTIONS** may cover — CSP report-only · autosend disabled ·
external AI/email providers not fully exercised · local Redis *only* with its durability limit and
recovery procedure explicitly accepted · non-critical observability gaps.

Declared exceptions are open items. Never record them as completed.
